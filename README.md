# SS14 Tactical DB

Веб-каталог химикатов и реакций Space Station 14 с каталогом билдов, регистрацией пользователей, избранным, комментариями и модерацией пользовательских материалов.

## Требования

- PHP 8.3+ с расширениями, которые требует Laravel (включая PDO-драйвер выбранной БД, `mbstring`, `xml`, `dom`, `fileinfo`, `openssl`, `tokenizer` и `ctype`).
- Composer 2.
- Node.js 20.19+ или 22.12+ и npm для сборки CSS/JS.
- Python 3.10+ и pip — используются существующим экстрактором SS14 для обработки игровых YAML-прототипов.
- SQLite для простого локального запуска либо MySQL/MariaDB для постоянного развёртывания.

> Реестр источников и манифестов хранится в `config/game_sources.php`. Python-экстрактор остаётся специализированным парсером YAML-прототипов; он читает этот Laravel-конфиг через PHP CLI, поэтому именно PHP-конфиг является источником истины для Laravel-синхронизации (старый список в `config.py` оставлен для совместимости с другими скриптами, но синхронизатор его переопределяет). Не удаляйте `ss14_chem_extractor.py`, пока его функциональность не будет отдельно перенесена и проверена на совпадение результатов.

## Локальный запуск (SQLite)

1. Установите PHP-зависимости:

   ```bash
   composer install
   ```

2. Создайте локальный файл окружения и ключ приложения:

   ```bash
   cp .env.example .env
   touch database/database.sqlite
   php artisan key:generate
   ```

   Проверьте, что в `.env` задано `DB_CONNECTION=sqlite`. Для SQLite остальные `DB_HOST`/`DB_DATABASE` не нужны.

3. Установите зависимости Python:

   ```bash
   python3 -m venv .venv
   . .venv/bin/activate
   pip install -r requirements.txt
   ```

   Команда синхронизации вызывает `python3` из `PATH`. Если вы используете виртуальное окружение, активируйте его перед запуском Laravel-команды или настройте `PATH` в окружении процесса планировщика.

4. Установите и соберите frontend:

   ```bash
   npm ci
   npm run build
   ```

5. Создайте таблицы и запустите сайт:

   ```bash
   php artisan migrate --force
   php artisan serve
   ```

   Откройте `http://127.0.0.1:8000`.

## Синхронизация химии

- `php artisan chemistry:sync` — скачивает YAML-манифесты всех форков из `config/game_sources.php`, обрабатывает их и транзакционно импортирует каталог в текущую БД.
- `php artisan chemistry:sync --file=/absolute/path/to/data.json` — импортирует подготовленный JSON, удобно для проверки/восстановления.
- `php artisan schedule:list` — проверяет расписание.
- `php artisan schedule:work` — запускает локальный процесс планировщика.

Синхронизация запланирована на каждый понедельник в 04:17 по часовому поясу приложения (`config/app.php`). На сервере вместо постоянного `schedule:work` рекомендуется добавить cron, запускающий `php artisan schedule:run` каждую минуту:

```cron
* * * * * cd /path/to/ss14-tactical-db && php artisan schedule:run >> /dev/null 2>&1
```

Если обновление не удалось или JSON неполный, команда завершится с ошибкой и не начнёт импорт. Сам импорт выполняется в транзакции. Повторный импорт использует upstream ID и не создаёт дубликаты. Каталог сайта читает данные из локальной БД; посетителям не требуется обращаться к GitHub при открытии страниц.

## Источники данных

`config/game_sources.php` содержит 21 игровой форк, включая URL репозитория, ветку, пути YAML-файлов, локализации, наследование и переопределения. При добавлении форка проверьте обязательные `raw_url`, `reagent_files` и `reaction_files`, а также при необходимости `parent_fork` и override-манифесты.

## Проверки

```bash
php artisan route:list
php artisan schedule:list
php artisan test
npm run build
python3 -m py_compile ss14_chem_extractor.py
```

`php artisan test` требует PHP-расширения для PHPUnit и доступного тестового драйвера БД. Для запуска на MySQL настройте `DB_*` в `.env` и убедитесь, что MySQL-драйвер PDO установлен.

## Безопасность и конфигурация

- Не публикуйте `.env`: он содержит ключ приложения и доступы к базе. В архив включён только `.env.example`.
- Первый зарегистрированный пользователь не получает роль администратора автоматически. Назначайте роль `admin` только доверенному пользователю через базу данных или уже существующую административную функцию.
- Не запускайте `migrate:fresh` на базе с нужными данными: команда удаляет таблицы.

## Каталог химикатов по игровым форкам

Страница `/reagents` показывает каталог источников, сформированный из импортированных записей `reagents.source_fork` и `reactions.source_fork`. Для каждого форка отображается количество реагентов и реакций; нажатие на карточку фильтрует каталог по этому источнику. Названия и акцентные цвета берутся из `config/game_sources.php`, когда источник сопоставляется с реестром. Поиск и фильтр категории продолжают работать внутри выбранного форка.

Если карточки форков пусты, проверьте, что в импортированном `data.json` у записей заполнено поле `source`, а после импорта оно записано в `source_fork`.


## Каталог форков и дополнительные инструменты

В текущей сборке выбор игрового форка находится в правой боковой панели и сохраняется в сессии. Фильтр применяется к каталогу реагентов, калькулятору, деревьям синтеза, ботанике, медбею и списку химических реагентов для ordnance.

Добавлены локальные разделы: `/botany`, `/medbay`, `/craft-trees`, `/maps`, `/ordnance`, `/antag`. Ботаника и медбей работают на полях реагентов, импортированных из `data.json`; деревья синтеза и планировщик ordnance разворачивают существующие рецепты до базовых ингредиентов.

**Ограничения данных:** текущий импорт `data.json` содержит химические реагенты и реакции, но не содержит самостоятельный набор станционных карт/координат, и не содержит модель боеприпасов (гильзы, blast falloff, урон, осколки). Поэтому локальная карта пока сообщает об отсутствии картографического набора, а ordnance-раздел считает только синтез ингредиентов и не выдумывает характеристики взрыва. Для полного паритета с оригиналом отдельно нужно перенести map extractor/assets и ordnance dataset/engine из оригинального проекта.

Оригинальный проект для сверки функций: https://github.com/MikameO/space-station-recipes

## Каталог предметов и конструктор экипировки

Каталог брони, оружия, боеприпасов, гранат, медицинских предметов и инструментов хранится в отдельной таблице `equipment_items`. Он не заменяет химическую базу и не меняет её данные.

```bash
# Сначала обновить схему MySQL
php artisan migrate --force

# Сканировать все игровые форки из config/game_sources.php и импортировать YAML-прототипы
php artisan equipment:sync

# Быстрая проверка только Vanilla (может всё равно скачать много YAML-файлов)
php artisan equipment:sync --fork=vanilla

# Тестовый запуск с ограничением файлов, НЕ для полной базы
php artisan equipment:sync --fork=vanilla --max-files-per-fork=5
```

Сборщик читает список репозиториев и веток из `config/game_sources.php`, получает дерево GitHub, загружает YAML-файлы предметов, обрабатывает SS14 `!type:`-теги и сохраняет `Prototype ID`, источник, путь к файлу, спрайт-путь, слоты, теги и компонентные данные. Для известных родителей компонентов выполняется ограниченное разрешение наследования. Это индекс прототипов, а не полноценный движок RobustToolbox: сложные системные зависимости и все runtime-эффекты игры здесь не симулируются.

Результаты кэшируются в `cache/equipment/` и JSON передаются в `storage/app/equipment-items.json`. Если GitHub недоступен, сканирование выдаст ошибку; импорт не начнётся при пустом результате. Повторный запуск обновляет существующие записи. Поиск в конструкторе ограничен выбранным форком, когда форк выбран в боковой панели; при выборе «Все форки» поиск может находить варианты из разных источников.

Названия, описания и прототипы берутся из игровых репозиториев; поле `source_url` сохраняет ссылку на исходный YAML. Перед публичным распространением производных игровых ресурсов необходимо соблюдать лицензию и атрибуцию соответствующего форка. Сами игровые спрайты пока не копируются: сохраняется только путь к ним в прототипе.

## Важное обновление каталога химии: наследование форков и рецепты

Выбранный форк теперь рассматривается как вариант игрового набора, а не как жёсткий фильтр `source_fork = selected`. В каталоге видны прототипы выбранного форка и его родителей, а также базовые vanilla-реагенты, если они не помечены `blocked` в `forkStatus`. Предметы собственного форка ранжируются выше базовых vanilla-записей.

Миграция `2026_10_22_181000_preserve_fork_chemistry_metadata.php` сохраняет `recipe`, `forkStatus`, `forkNotes`, `alsoIn` и дополнительные поля из `data.json`. Чтобы заполнить эти новые колонки для уже импортированных данных, после миграции повторно импортируйте имеющийся файл:

```bash
php artisan migrate --force
php artisan chemistry:sync --file=data.json
```

Страница реагента показывает описание, эффекты/метаболизм и рецепт из `data.json`, даже если импортёр не смог создать отдельную запись реакции. Для реакций дополнительно показываются статус `modified`/`blocked` и заметки форка, если эти данные присутствуют в JSON.

Ограничение источника данных: текущий формат `data.json` хранит единое каноническое описание реагента и не всегда содержит полные поля каждой переопределённой версии одного и того же Prototype ID. В таких случаях сайт может показать статус/заметку о различии, но не может восстановить отсутствующие в JSON значения изменённого реагента без дополнительного извлечения fork-specific override из YAML исходного репозитория.

## Человекочитаемые свойства предметов и цвета реагентов

Каталог предметов теперь формирует русскоязычные пояснения из сохранённых YAML-компонентов: числовые множители скорости показываются как изменение в процентах (например, `WalkSpeedModifier: 1.3` → «увеличивает скорость ходьбы на 30%»), а коэффициенты защиты брони — как снижение/увеличение соответствующего типа урона. Неизвестные компоненты сохраняются и показываются через общий форматтер, а не отбрасываются allow-list фильтром.

Для брони и оружия каталог пробует загрузить PNG-кадры спрайта из `.rsi` по `Sprite.state`/`layers[].state`. Если у конкретного предмета путь или состояние не разрешается в PNG, карточка автоматически скрывает пустое изображение и сохраняет ссылку на исходный YAML.

В карточках химикатов отображается цветовой образец, приблизительное русское название оттенка и исходный HEX. Название оттенка — визуальная подсказка, HEX остаётся исходным значением из данных игры.

Чтобы обновить расширенные компоненты предметов в уже существующей базе MySQL, запусти из корня проекта:

```bash
php artisan equipment:sync
```

Повторный сборщик обновит записи каталога экипировки; повторно импортировать химию не требуется.
